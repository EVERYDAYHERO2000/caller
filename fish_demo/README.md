# fish_demo — скорость и стриминг голоса Fish Audio

Демостенд для Realtime TTS v3 от Kitta (fishaudio.org — неофициальный посредник Fish Audio).

```
браузер ──JSON + mp3-чанки──▶ server.py ──MessagePack / WebSocket──▶ wss://realtime.fishaudio.org/v3/tts/live
```

API-ключ хранится в `fish_demo/.env` (`FISH_API_KEY=...`) и в браузер не передаётся.

## Запуск

```bash
.venv/bin/pip install -r fish_demo/requirements.txt
.venv/bin/python fish_demo/server.py      # http://localhost:8765
```

## Что показывает

- **Стрим: весь текст сразу** — фраза отправляется одним сегментом, звук играет по мере прихода чанков (MediaSource).
- **Стрим: как ответ LLM** — слова «печатаются» с заданной скоростью, сегменты уходят в синтез по концу предложения
  (опционально первый — уже по запятой). Так работает голосовой агент поверх стримящей LLM.
- **HTTP целиком** — обычный синхронный запрос для сравнения.
- **Прогретое соединение** — WebSocket-сессия открывается заранее (как в начале звонка), чтобы не платить ~1.5–2 с
  за подключение на каждой реплике.

- **Заготовки хезитаций** («Ммм...», «Так...», «Секундочку...») — генерируются в Fish тем же голосом один раз
  (кнопка «Сгенерировать для голоса», ≈45 кредитов, файлы в `static/fillers/<voiceId>/`). Если ответа нет дольше
  заданного порога (по умолчанию 400 мс), играет заготовка, ответ стартует сразу после неё. Нажатие кнопки = абонент
  договорил; «первый токен через N мс» имитирует время, пока LLM думает.

Метрики: время до первого звука (реальный старт воспроизведения в браузере), первый чанк от API, подключение,
длительность генерации и аудио, паузы в воспроизведении; таймлайн чанков; история запусков.

## Что выяснили о протоколе

- Режим `simple` синтезирует **один** сегмент и закрывает сессию — для диалога нужен `reliable`
  (`text` с `sequence` → `flush` с `segmentId`; `stop` закрывает сессию).
- `format: "pcm"` сейчас не работает (`provider_unavailable`), используем mp3.
- **Одно WebSocket-соединение на ключ** (второе — `permission_denied: Concurrent connection limit exceeded`);
  после обрыва посреди генерации слот может оставаться занятым больше 15 минут.
- Отдельная API-квота (`api_quota_remaining`), не равна кредитам сайта. Flash ≈ 0.25 кредита за русский символ.
- Цифры из первых замеров (сентябрь 2026): подключение 1.2–2 с, от `flush` до первого чанка ≈ 1.0–1.3 с,
  HTTP-запрос целиком ≈ 4–5 с. Чанки приходят примерно в темпе воспроизведения.

## Yandex Realtime API в режиме «только текст» (`yandex_text_mode_test.py`)

Проверено 2026-09-26, модель `speech-realtime-250923`:

- `session.update` с `"output_modalities": ["text"]` (без `audio.output`) — **работает**: аудио не приходит,
  распознавание, server VAD и автоматический ответ продолжают работать.
- `response.create` с `"response": {"output_modalities": ["text"]}` в audio-сессии — **не работает**, аудио всё равно идёт.
- Текст ответа приходит почти целиком (1–2 `response.output_text.delta`), а не по словам.
- Задержки от реального конца речи абонента (3 прогона): `speech_stopped` ≈ 380–400 мс, текст ответа ≈ 400–460 мс;
  в audio-режиме первое аудио Яндекса ≈ 670–815 мс. С Fish (+1.0–1.3 с) ответ ожидается через ≈ 1.5–1.8 с —
  заготовку можно запускать сразу по `speech_stopped`.
- Server VAD Яндекса закрывает реплику на паузах ~200 мс после законченной по смыслу части
  («Здравствуйте!», «Подскажите, пожалуйста,»), несмотря на `silence_duration_ms: 800`.

## Имитация звонка (`call_sim.py`)

Настоящий `AgentSession` + `AudioPort` без модема: «абонент» — фразы голосом macOS Milena в 8 кГц,
результат — стерео-WAV в `fish_demo/out/` (слева абонент, справа агент) и тайминги реплик.

```bash
.venv/bin/python fish_demo/call_sim.py            # Fish + заготовки
.venv/bin/python fish_demo/call_sim.py --yandex   # голос Яндекса для сравнения
.venv/bin/python fish_demo/call_sim.py --barge    # абонент перебивает длинный ответ
```
